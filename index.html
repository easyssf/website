Shared Signals Framework
support for Java, .NET, Go and Rust

easyssf adds an OpenID Shared Signals Framework (SSF) receiver to your Java, .NET, Go or Rust application, so that it reacts when your identity provider revokes a session, changes a credential, or signals a risk.
The receiver verifies the incoming security events, CAEP events about sessions and credentials, RISC events about accounts, and SCIM Events about changes to your users, rejects the affected access tokens, ends the affected sessions, and hands everything else to your code.

Why a SSF receiver?

Your identity provider knows the moment a user signs out everywhere, loses a device, changes a password or trips a risk rule. Your application does not: its session and its access tokens stay valid until they expire. A Shared Signals receiver closes that gap.

Without a receiver

You shorten token lifetimes, poll token introspection on every request, or write the Security Event Token verification, replay protection and stream management yourself. OpenID back-channel logout covers logout only, and a logout request that gets lost on the way stays lost: there is no retry and nothing to poll. It says nothing about credentials, risk or provisioning either.

With easyssf

The receiver verifies the events and acts on them: it rejects the revoked tokens and ends the sessions in the security layer of your framework, out of the box. The events it cannot act on alone, it hands to a handler of yours. One library, one behaviour, on the JVM, .NET, Go and Rust. Get started with the integration for your framework.

How it works

A transmitter, usually your identity provider, delivers Security Event Tokens (SETs) to your application, either by pushing them to an endpoint or by letting the application poll for them. easyssf verifies each token, skips duplicates and routes the events to the integrations that act on them.

Push or pollRFC 8935 · RFC 8936

A push endpoint on a route of your choice, secured by its own stateless filter chain, or a poller that fetches and acknowledges SETs from the transmitter, with long polling if you want it. Acknowledgements survive a restart, and several instances can share a stream.

Every SET verifiedRFC 8417

Signature against the transmitter's JWK Set, discovered from its .well-known/ssf-configuration, plus typ, iss, aud, jti, iat and events. The transmitter and every endpoint it publishes must use HTTPS.

Resource server integration

A CAEP session-revoked event makes the application reject the access tokens of that session, or all tokens of the user issued before the event: built into the Spring Boot starter, a few lines with quarkus-oidc.

OIDC client integration

session-revoked and credential-change events invalidate the matching local sessions, by session id, subject or email.

SCIM EventsRFC 9967

The provisioning changes of a SCIM service provider, users created, patched, deactivated or deleted, arrive as SETs with a scim subject. SsfScimEventHandler hands them to a method per operation, and a deactivation ends the user's sessions.

Stream management

Let the application create or update its stream at the transmitter on startup, verify it, and use the whole stream management API through SsfStreamClient. Several transmitters, several Keycloak realms say, are each configured by name; the issuer of a SET selects the one that verifies it.

Production details covered

State in your database when there is one, with migration scripts for the schema, Micrometer metrics, a health indicator for Actuator or SmallRye Health, retries with backoff, and the application starts even while the transmitter is down. Processing is at least once; every SET carries an idempotency key for the side effects of your handlers.

Use cases

What a receiver does with the events. The first three are the example applications, each for Spring Boot, Quarkus, .NET, Go and Rust with a Keycloak setup to run against; the others are handlers of your own.

Reject revoked access tokens

An OAuth2 resource server trusts an access token until it expires. With a CAEP session-revoked event the API learns that the session is over and rejects the tokens of that session, or all tokens of the user issued before the event, from the next request on. Built into the Spring Boot starter; a few lines on top of quarkus-oidc in Quarkus.

Example: Spring Boot · Quarkus · .NET · Go · Rust

End the sessions of a web application

An OpenID Connect relying party keeps its own session after the login. When the identity provider ends the session or the user changes a credential, session-revoked and credential-change events let the application find the local session by session id, subject or email and end it, so that the next request goes through the login again.

Example: Spring Boot · Quarkus · .NET · Go · Rust

Mirror users from SCIM Events

A SCIM service provider reports the changes of its users as SCIM Events, RFC 9967, instead of being polled. The application mirrors them into its own directory with a handler per operation, and a deactivation or deletion also ends the user's sessions. The example runs without an identity provider, driven by the test transmitter, because Keycloak does not emit SCIM Events.

Example: Spring Boot · Quarkus · .NET · Go · Rust

React to RISC account events

RISC events report what happened to the account itself at the identity provider. An account-disabled event, for a hijacked account say, is the moment to lock the local account and end its sessions; account-enabled lifts the lock; account-purged says the account is gone for good, so the user's data can go too. credential-compromise and the identifier events work the same way. Your SsfEventHandler gets each event with its subject and decides.

See React to any event in Getting started, and the RISC events on the tools page.

Track sessions for threat detection

Not every receiver protects its own sessions; some watch. A session-established event reports a login with the IP addresses, the user agent fingerprint and the authentication context, and session-presented that the session was used to sign in to another application. An endpoint or identity threat detection service, EDR or ITDR, consumes them to build a timeline per user, spot sign-ins from new places and lateral movement across applications, and alert the security team or have the identity provider revoke the session.

See the session events on the tools page, and React to any event in Getting started.

@Component
class StepUpHandler extends SsfCaepEventHandler {

    @Override
    protected void onAssuranceLevelChange(SsfCaepEvent event, SsfEventContext eventContext) {
        if ("decrease".equals(event.changeDirection())) {
            SsfSubject subject = eventContext.subject();
            // subject.subject(), subject.sessionId(), subject.email(), event.currentLevel() ...
        }
    }

}

Assemble the receiver

A metadata resolver and a verifier for the transmitter, a processor that de-duplicates and dispatches to your handlers, and a push handler or a poller for the delivery method of your stream. The code below is the whole of it.

Wire it into your framework

Call the push handler from the endpoint the transmitter posts SETs to and return its status and body, or start the poller from your scheduler. Create the stream at the transmitter, or let SsfStreamClient do it; SsfTransmitter assembles the parts for one transmitter and wakes the poller up as soon as the stream is registered.

All of it in one place

SsfHttpClient httpClient = new JdkSsfHttpClient();
String issuer = "https://idp.example/realms/demo";

SsfTransmitterMetadataResolver metadata = new SsfTransmitterMetadataResolver(issuer, null, httpClient);
NimbusSsfSetVerifier verifier = new NimbusSsfSetVerifier(issuer,
        () -> metadata.resolve().jwksUri().toString(), httpClient);
verifier.setExpectedAudience("https://my-app.example");

SsfEventHandler handler = (eventContext) -> {
    if (eventContext.hasEvent("CaepSessionRevoked")) {
        SsfSubject subject = eventContext.subjectFor("CaepSessionRevoked");
        // end the session subject.sessionId() of the user subject.subject()
    }
};
SsfSetProcessor processor = new SsfSetProcessor(verifier, new InMemorySsfJtiDedupStore(10_000), List.of(handler));

// PUSH: call this from the endpoint the transmitter posts SETs to
SsfPushHandler pushHandler = new SsfPushHandler(processor, "Bearer " + pushSecret);
SsfPushResponse response = pushHandler.handle(authorizationHeader, requestBody);

// POLL: fetch SETs from the transmitter instead
SsfPoller poller = new SsfPoller(httpClient, tokenProvider, () -> pollEndpoint, processor);
poller.start();

Handlers run before the SET is acknowledged. If one throws, the push handler answers with an error and the poller does not acknowledge the SET, so the transmitter delivers it again. A SET is claimed in the de-duplication store while its handlers run, so two instances never acknowledge a SET one of them failed on; eventContext.idempotencyKey() is the key for a handler's side effects.

There is no example application for plain Java yet; the README walks through the assembly, and the handlers of the Spring Boot and Quarkus examples are plain Java you can reuse.

class StepUpHandler(IStepUp stepUp) : SsfCaepEventHandler
{
    protected override Task OnAssuranceLevelChangeAsync(SsfCaepEvent caepEvent, SsfEventContext eventContext,
            CancellationToken cancellationToken)
    {
        return (caepEvent.ChangeDirection == "decrease")
            ? stepUp.RequireAsync(eventContext.Subject.Subject, caepEvent.CurrentLevel, cancellationToken)
            : Task.CompletedTask;
    }
}

type stepUp struct{ receiver.NoopCaepHandler }

func (stepUp) OnAssuranceLevelChange(ctx context.Context, event *caep.Event, set *receiver.Context) error {
    if event.ChangeDirection() == "decrease" {
        return requireStepUp(ctx, set.Subject().Sub(), event.CurrentLevel())
    }
    return nil
}

struct StepUp;

impl SsfCaepEventHandler for StepUp {
    async fn on_assurance_level_change(&self, event: SsfCaepEvent, context: SsfEventContext) -> Result<(), BoxError> {
        if event.change_direction().as_deref() == Some("decrease") {
            step_up.require(context.subject().subject(), event.current_level()).await?;
        }
        Ok(())
    }
}

Subjects as the spec defines them

SsfSubject is the sub_id of the SET: a subject identifier in any RFC 9493 format (iss_sub, email, opaque, account, phone_number, did, uri, aliases), the scim format of RFC 9967, or a complex subject with its user, session, device, tenant and other members. Shortcuts cover the common cases, nothing is lost.

Your own event type aliases

The SSF, CAEP and RISC event types have built-in aliases such as CaepSessionRevoked. Register aliases for vendor specific event types, in configuration or in code, and use them wherever an event type is named. The URIs stay canonical; an alias can never redefine another.

Interoperability

Keycloak

Tested with the SSF transmitter of Keycloak 26.8 (--features=ssf). The examples ship a pre-configured realm, and the README documents Keycloak's audience, scopes and single-stream rule.

caep.dev

Point the receiver at caep.dev, SGNL's free hosted transmitter, to receive CAEP events sent from a browser without running an identity provider. See Tools.

OpenID conformance suite

The receiver test plans of the OpenID conformance suite, default and CAEP interop profile with push and poll delivery, run against the receiver in an automated test module.

Standards

Built on the OpenID Shared Signals specifications and the IETF security event RFCs, see Specifications for the complete list and what easyssf takes from each.
